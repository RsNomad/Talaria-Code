## ADR-025-D — CA-16 outcome (R2-1, WS-R2)

**Outcome (task R2-1, WS-R2):** `handleRecheck`'s agent-probe section (the `scope === 'all' || scope === 'agent'` branch) now runs its `locatePipx` call under a `'recheck'`-keyed latch, mirroring `handleInstall`'s exact `arm`/`try`/`finally { release }` pattern. Before this task, that branch fired `await this.deps.locatePipx()` with no signal and no latch entry — `dispose()`'s `this.latches.abortAll()` (`:732`) had nothing to reach, so the probe outlived teardown and a late resolve could still write `this.lastAgentIssue`. `latchRegistry.ts` is **0-diff** — `arm(key): AbortController | undefined` already returned the controller (critic I-18); this task only calls it under a new key.

A recheck that arrives while an agent probe is already in flight **coalesces** onto it instead of refusing or re-arming: `if (!this.latches.has('recheck'))` guards the arm/probe/release block, so a concurrent call skips straight through to the method's existing single completion `bumpStatus()` + `{ ok: true }`. This is deliberate, not an oversight — a second `arm('recheck')` would overwrite the `Map` entry under the same key, orphaning the first `AbortController` so `dispose()` could never reach it again (the exact hazard this task closes, reintroduced). Recheck is a read-only status refresh, so refusing the second caller with `{ ok: false }` would surface a spurious error for a panel that just asked to repaint; coalescing is honest because the in-flight probe already covers the agent state the second call asked for. The latch is scoped to the agent-probe section only (not the whole method) — a concurrent `scope: 'all'` recheck still runs its `os`/`llamacpp` rekick work above the guarded block untouched. ### OD-I policy deliverable: lock-test discipline (ADR-FSU-02) + LOCK INDEX

**Policy** (reproduced verbatim from the FSU remediation architecture's own "Target design (ADR-FSU-02)" §1, `.superpowers/plans/2026-09-06-lens-r2-fsu-remediation-arch.md`; no standalone `docs_claude/adr/ADR-FSU-02-lock-discipline.md` file was ever created — this ADR, not that path, is the durable record OD-I's own row commits to):

> A source-scan lock is legitimate only when (a) the source of truth cannot be imported (foreign package / true frozen zone) or (b) it guards a security invariant that has no type-level expression; a lock must be scoped to the real sink and **must never dictate production shape**; every lock is registered in the ADR's index with its invariant, allowed shapes and RED probe. Duplicates guarded by drift-locks are consolidated (export + import) and the lock deleted.

FI-22's `DEFAULT_ENDPOINTS` case is the textbook instance of the failure mode this policy retires: no security invariant and no foreign/frozen source justified the duplication — an ordinary `export`/`import` (this task) was always available, and the two copies existed only because nobody had done it yet. FI-21's three sites (ADR-025-R/S/T) are the OTHER failure mode: a lock that, by being blunter than the invariant it actually protects (a bare-identifier receiver scan, an unscoped tool-name-literal ban, a field-name-blind spread ban), pushed PRODUCTION into an unnatural shape to dodge a false positive — the "must never dictate production shape" clause, restored in each case by either re-scoping the lock (FI-21 site 2, already fixed upstream at W3 T8a) or sanctioning the natural shape (FI-21 sites 1 and 3) rather than loosening the lock's real guarantee.

**LOCK INDEX.** Every source-scan lock in the repo as of this task's HEAD — a lock defined as: reads its own subject's RAW SOURCE TEXT (or, for `configScope.test.ts`, `package.json`'s parsed KEY set) from disk and applies a regex/string-membership/byte-hash check against it, as opposed to importing and calling real functions. ## ADR-025-V — `settleAsyncVerb` collapses the five LSP handler timeout/error arms (task F10-1, WS-F10 kickoff, FI-25)

1. **The TS-narrowing trap (avoided).** A `settleAsyncVerb(...): ToolResult | undefined` sketch does not work: after `if (early !== undefined) return early;` in the CALLER, TS still sees the original `run` union in full — the timeout/error variants of `GatewayVerdict<T>` have no `.value`, so a subsequent `run.value` is a compile error, and forcing it with `as`/`!` is banned. `settleAsyncVerb` instead returns a DISCRIMINATED result, `{ readonly early: ToolResult } | { readonly value: T; readonly status: 'ok' | 'maybe-indexing' }`. The narrowing happens INSIDE the helper (two early `return`s on `run.status`, ordinary discriminated-union control-flow narrowing — no `as`/`!` needed there either), and the caller narrows its own OWN `settled` value via `'early' in settled`, after which `settled.value`/`settled.status` are typed exactly as `run.value`/`run.status` were after the old handler's own two early returns.
2. **`handleLocationsTool`/`handleDocumentSymbols`/`handleWorkspaceSymbols`/`handleHover` — direct collapse.** All four already call `runAsyncVerbWithRetry`, whose return type (`GatewayVerdict<T>` — `{status:'ok'|'maybe-indexing';value:T} | {status:'timeout-partial'} | {status:'error';error}`) IS the shape `settleAsyncVerb` accepts, so each site passes its `run` straight through, unchanged.
