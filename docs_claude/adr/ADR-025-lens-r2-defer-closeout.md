## ADR-025-D — CA-16 outcome (R2-1, WS-R2)

**Outcome (task R2-1, WS-R2):** `handleRecheck`'s agent-probe section (the `scope === 'all' || scope === 'agent'` branch) now runs its `locatePipx` call under a `'recheck'`-keyed latch, mirroring `handleInstall`'s exact `arm`/`try`/`finally { release }` pattern. Before this task, that branch fired `await this.deps.locatePipx()` with no signal and no latch entry — `dispose()`'s `this.latches.abortAll()` (`:732`) had nothing to reach, so the probe outlived teardown and a late resolve could still write `this.lastAgentIssue`. `latchRegistry.ts` is **0-diff** — `arm(key): AbortController | undefined` already returned the controller (critic I-18); this task only calls it under a new key.

A recheck that arrives while an agent probe is already in flight **coalesces** onto it instead of refusing or re-arming: `if (!this.latches.has('recheck'))` guards the arm/probe/release block, so a concurrent call skips straight through to the method's existing single completion `bumpStatus()` + `{ ok: true }`. This is deliberate, not an oversight — a second `arm('recheck')` would overwrite the `Map` entry under the same key, orphaning the first `AbortController` so `dispose()` could never reach it again (the exact hazard this task closes, reintroduced). Recheck is a read-only status refresh, so refusing the second caller with `{ ok: false }` would surface a spurious error for a panel that just asked to repaint; coalescing is honest because the in-flight probe already covers the agent state the second call asked for. The latch is scoped to the agent-probe section only (not the whole method) — a concurrent `scope: 'all'` recheck still runs its `os`/`llamacpp` rekick work above the guarded block untouched.
