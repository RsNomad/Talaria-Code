# ADR-023 — WS-MCP-SECRET: manual `mcp.add` secrets go to Hermes `.env` config-first, config.yaml keeps only `${MCP_<NAME>_<KEY>}` (AU-59)

**Status:** Accepted (2026-09-05, "Линза доработок" WS-MCP-SECRET). **Finding:** AU-59 (Secrets UI, Low-Med — CF-13 parity for the manual add).

## Context
The manual "Add MCP server" path collected env via a plaintext webview textarea, sent the values inline in `mcp.add`, and Hermes wrote them literally to `~/.hermes/config.yaml` — a file dumped raw over the tui_gateway wire on every MCP-panel refresh, round-tripped by the dashboard mcp.json editor and carried by config backups. The catalog path (AU-41) already collects secrets host-side, masked, into Hermes' `~/.hermes/.env` (secret scope, listed masked, in no config dump). Hermes ships every primitive needed to close the gap without a Hermes change: `PUT/GET/DELETE /api/env`, config-wide `${VAR}` interpolation (`tools/mcp_tool.py` `_interpolate_env_vars`, runtime load AND test-probe paths), and its own `MCP_<SUFFIX>_API_KEY` + `Bearer ${MCP_<SUFFIX>_API_KEY}` idiom for CLI-added HTTP servers (`hermes_cli/mcp_config.py` `_env_key_for_server`).

## Decision
1. **Names only on the wire.** `McpAddParams` (stdio) gains `secretEnvNames: string[]`; the value is never typed into the webview, never in the `mcp.add` params, collected host-side via `promptSecret` (masked `showInputBox`) AFTER the consent modal — the same binding as the catalog path.
2. **Namespaced `.env` keys: `MCP_<SUFFIX>_<KEY>`** (Hermes' `_env_key_for_server` suffix rule, generalized). Differs from the catalog path on purpose: a catalog entry declares its own canonical var names and its config references them by those names; a manual add has no spec, so an un-namespaced `GITHUB_TOKEN` would clobber the user's global one. The prefix also makes a writer-denylist hit impossible by construction.
3. **CONFIG-FIRST, fail-closed ordering** (`McpAdminHandler.addWithSecretEnv`): `POST /api/mcp/servers` with `env[name] = "${MCP_…}"` → `PUT /api/env` per secret → Layer-6 `GET /api/env` (`is_set:true` for every key — managed/container mode answers the PUT `{ok:true}` while writing nothing) → `reload.mcp`. On ANY failure after the POST: `DELETE /api/env` for written keys (secret residue first), then `DELETE /api/mcp/servers/{name}`; compensation failure is disclosed (the leftover entry holds only `${…}` references). Rejected: env-first (a 409 on the POST would already have overwritten a same-named `.env` key; a crash between steps would leave the SECRET as residue rather than a secret-free reference).
4. **Client-side value gate:** printable ASCII ≤ 4096 (`checkSecretValue`) — `save_env_value` silently strips non-ASCII/CR/LF, so a lookalike-glyph paste would persist mangled; refusing beats mangling.
5. **D-lite for the surface that stays:** the plaintext Env field gets a non-secret placeholder showing the `${KEY}` idiom, an always-rendered `aria-describedby` caption, `autocomplete=off`/`spellcheck=false`; the consent modal partitions env keys into plaintext-stored vs `${KEY}`-resolved and WARNS (never refuses) on credential-shaped plaintext keys via `CREDENTIAL_NAME_CORE` — the redaction belt's deny-list minus `env`, extracted behaviour-identically (`SECRET_KEY` recomposed from it; existing redaction tests untouched).

## Consequences
- Secret values exist only in `mcpAdd`'s call stack and in the single `PUT /api/env` body over loopback; never in config.yaml, logs, thrown messages, webview state, or gateway dispatches (pinned by `mcpAdminHandler.secretEnv.test.ts`'s leak-surface assertion).
- `mcp.add` still rides `ConfigWriteTail`; the masked prompts extend the window the consent modal already holds.
- The `.env`-at-rest guarantee is Hermes' (`_secure_file` 0600 unless a pre-existing mode is preserved; skipped in managed mode — which Layer 6 turns into a rollback).
- **Non-goals (documented, not built):** `mcp.remove` does not delete `MCP_<SUFFIX>_*` keys from `.env` (Hermes' own CLI path doesn't either; a stale key is overwritten on re-add and holds no reference back into config). Two server names that normalize to the same SUFFIX (`my-server` / `my.server`) share `.env` keys — Hermes' own idiom has the identical property; the consent modal names the exact key so the user sees it.
- Secret env NAMES use the module's plaintext env-key charset (`^[A-Z_][A-Z0-9_]{0,63}$`, a strict subset of Hermes' `^[A-Za-z_][A-Za-z0-9_]*$`) because each name is also written as a key into the server's `env` map.
- Runtime resolution (`${MCP_…}` → value on load and on `mcp.test`) and the `.env` re-read after `reload.mcp` are Hermes behaviours we only read — proven live by the owner on Fedora (plan Task 7), not by unit tests.
